- **배포 버전**: `e23ddfa2-20d1-47be-b7af-1e772668a4c1` (people-os, 2026-11-23)
- **운영 D1**: 마이그레이션 `0046_task_lists.sql` 적용 (추적 테이블 `d1_migrations` 마지막 행 = 0046)
- **커밋하지 않았다.** 변경은 작업 트리에 있다.
- **화면은 브라우저로 확인하지 못했다** (이 세션에 브라우저 도구가 없다). API는 로컬·라이브에서 확인했고, 화면 스크립트는 `node --check` 통과와 정적 파일 200까지만 확인했다. **브라우저에서 할 일 탭을 한 번 눌러 보는 것이 남았다** (아래 4장).

### 스키마 (0046)

- `task_lists(id, owner_id, title, is_default, created_at)`. 기본 목록 id는 `tl_default_<owner_id>`로 정해져 있어 PRIMARY KEY가 "소유자당 1개"를 보장한다. 미지정 할 일의 목록은 `tl_default_unassigned` ("미지정 할 일").
- `tasks` 추가 컬럼: `list_id`, `details`, `due_date`, `due_time`, `starred`, `repeat_rule`, `repeat_group`, `parent_id`, `position` + **`starred_at`** (프롬프트에 없던 컬럼 — "최근 별표" 정렬에 필요해서 넣었다).
- 워크플로우 `create_task` 노드는 지금도 `INSERT INTO tasks (id, title, source, owner_id)`로 넣는다 (건드리지 않았다). 그렇게 들어온 행은 `list_id`가 비어 있고, **목록·할 일을 읽을 때** 소유자의 기본 목록으로 채운다 (`healTaskLists`).

### API

- `GET/POST /api/task-lists`, `PATCH/DELETE /api/task-lists/:id`. 응답에 목록별 진행 중 개수(`open_count`)가 있다.
- `GET /api/tasks?list=&filter=starred&sort=myorder|date|deadline|starred|title`. 기존 필드는 그대로이고 새 필드와 `indent`(0/1), `sort`, `today`를 더했다.
- `POST /api/tasks`: `details, due_date, due_time, starred, repeat_rule, list_id, parent_id` 추가.
- `PATCH /api/tasks/:id`: 위 필드 + `title`, `position`, `done`. **본문에 아는 필드가 하나도 없으면 지금까지처럼 완료 여부를 뒤집는다** (홈 카드의 체크박스가 그렇게 부른다). 응답에 `completed`(함께 완료된 개수), `next`(새로 만든 다음 회차 id), `task`를 더했다.
- `DELETE /api/tasks/:id`: 하위 작업도 함께 지운다 (`deleted` 개수).

반복 규칙 모양:

```json
{ "every": 1, "unit": "week", "weekdays": [1, 3], "ends": "after", "occurrences": 30 }
{ "every": 1, "unit": "month", "day": 31 }            // day: 1~31 | "last"
{ "every": 1, "unit": "month", "nth": "last", "weekday": 5 }  // nth: 1~4 | "last"
{ "every": 3, "unit": "day", "ends": "on", "until": "2026-12-31" }
```

서버가 `start`(= 설정할 때의 `due_date`)를 채워 저장한다. 반복 시간은 그 할 일의 `due_time`이다.

## 3. 프롬프트와 다르게 했거나 정해서 넣은 것

1. **`POST /api/tasks`의 제목은 200자를 넘으면 거절하지 않고 자른다** (지금까지의 동작). "할 일로 저장"이 문서 요약의 긴 액션 문장을 그대로 보내기 때문이다. `PATCH`로 제목을 고칠 때는 1~200자가 아니면 400이다.
2. **"날짜"와 "기한" 정렬이 거의 같다.** Google에는 날짜와 별개의 기한(Deadline) 필드가 있는데 이번 스키마에는 날짜 하나뿐이다. "날짜"는 날짜만, "기한"은 날짜+시간으로 줄 세운다. 기한 필드를 따로 둘지는 결정이 필요하다.
3. **반복 할 일의 다음 회차는 "지금 회차 날짜보다 뒤이면서 오늘 이후"인 첫 일정이다.** 오래 밀린 할 일을 완료했을 때 이미 지난 회차가 또 생기지 않게 했다. Google의 실제 동작은 확인하지 못했다.
4. **31일이 없는 달의 "매월 31일"은 그 달 마지막 날로, 평년의 2월 29일은 2월 28일로 당긴다.** Google이 건너뛰는지 당기는지는 확인하지 못했다.
5. **Ends: After N은 같은 반복 그룹의 완료된 회차 수로 센다** (프롬프트대로). 그래서 완료된 회차를 지우면 횟수가 다시 늘어난다.
6. **다음 회차는 제목·메모·시간·별표·목록·출처를 물려받고, 하위 작업은 물려받지 않는다.**
7. **날짜를 지우면 시간과 반복도 함께 지운다.** 반복 할 일은 하위 작업으로 넣을 수 없다 (400).
8. **"미지정 할 일" 목록은 모든 로그인 사용자에게 보인다** (미지정 할 일이 지금도 모두에게 보이는 것과 같은 범위). 이름 변경은 관리자만 된다.
9. **관리자는 본인 기본 목록이 자동으로 생기지 않는다** ("관리자 계정에 쌓지 않는다"는 기존 원칙). 관리자가 새 목록을 만들 때는 사용자 필터나 담당자 드롭다운에서 고른 사용자의 목록이 된다.
10. **담당자 배지는 관리자 화면과 미지정 할 일에만 보인다.** 전에는 일반 사용자에게도 줄마다 본인 이름이 붙었다.

## 4. 남은 한계

- **브라우저 확인 없음.** 볼 것: 목록 칩 전환, 행을 눌러 상세 펼치기, 제목·메모가 칸을 벗어날 때 저장되는지, 오늘·내일 버튼, 반복 대화상자(단위를 바꾸면 요일·매월 칸이 바뀌는지), 별표, 목록 이동, 하위 작업 추가, "완료됨 (N)" 접기, 기한 지난 날짜의 빨간색, 관리자 바와 목록 칩이 함께 움직이는지, 홈 카드의 할 일 체크.
- **끌어서 순서 바꾸기 없음.** "내 순서"에서는 상세의 위·아래 버튼으로 한 칸씩 옮긴다 (`PATCH position`).
- **목록 메뉴의 Print list / Delete all completed tasks / Clean up old tasks는 만들지 않았다** (구현 범위 밖).
- **시간 지정 알림 없음.** 날짜·시간은 표시와 정렬에만 쓰인다. 캘린더에도 나타나지 않는다.
- **워크플로우가 만든 할 일의 기한은 여전히 제목에 들어간다** (`(기한 …)`). `create_task` 노드가 새 `due_date` 컬럼을 쓰게 하려면 워크플로우 코드를 고쳐야 한다 (이번 범위 밖).
- **아침 브리핑(`digest.ts`)은 그대로다.** 하위 작업도 할 일 1건으로 센다 (Google과 같은 셈법, 홈 개수도 같다).
- 로컬 하네스(`harness/`)의 D1 상태·로그는 커밋 대상이 아니다.
